# Documentation site with a generated ABI reference

Closes the gap where the only documentation was a README and a 5-tab UI: a
`docs/` source tree that builds into a real static site, deployed by CI, and
reachable from the app. The contract ABI reference on that site is generated
from `lib/constants.ts` at build time, so it cannot drift from the endpoints the
app actually calls.

## What is here

### The site

`docs/*.md` — five pages, in the app's own visual language:

| Page                      | Covers                                                        |
| ------------------------- | ------------------------------------------------------------- |
| `docs/index.md`           | What Synapse Core is, when to use it, where to go next        |
| `docs/getting-started.md` | Install, run, configuration, mock vs live data, scripts       |
| `docs/architecture.md`    | Data flow, the Soroban layer, wallet layer, module boundaries |
| `docs/contract-abi.md`    | Every endpoint, generated (see below)                         |
| `docs/contributing.md`    | Tests, CI expectations, PR conventions, the docs site itself  |

```bash
npm run docs:build   # docs/*.md -> docs-dist/
npm run docs:dev     # build, then serve on http://localhost:4173
```

Output is plain HTML plus one stylesheet and one script, written as
`<slug>/index.html` so it works on any static host. `docs-dist/index.html`
mirrors `docs-dist/index/index.html` so the index is also the site root.

### The generated ABI reference

`docs/contract-abi.md` contains one anchor:

```html
<!-- generated:abi-reference -->
```

The build replaces it with a table generated by `scripts/docs/abi-reference.mjs`,
which transpiles `lib/constants.ts` with the `typescript` package already in
`devDependencies`, imports the result, and renders `ABI_ENDPOINTS`. There is no
second copy of the ABI anywhere in the repository.

Adding an endpoint to `ABI_ENDPOINTS` and rebuilding is the whole workflow. If
the anchor or its `generated: abi-reference` front matter is removed, the build
**fails** rather than quietly emitting a page with no table on it.

### Deployment

`.github/workflows/docs.yml` builds on `main` and deploys to GitHub Pages.
`--base` and `--site` are derived from `github.repository` rather than
hardcoded, because a Pages _project_ site is served from `/<repo>/` and a site
built for `/` 404s on every asset. A workflow step fails the build if any
absolute `/assets` path survives into the output, which is the failure mode a
silently-unapplied base would produce.

A pull request that touches `docs/`, `scripts/docs/`, `lib/constants.ts`, or the
workflow runs the docs build as a check. The deploy job is gated to pushes on
`main`; the workflow does not request `pages: write` for pull requests, which a
fork could not be granted anyway.

### Reachability

- `DOCS_SITE_URL` in `lib/constants.ts` (override with `NEXT_PUBLIC_DOCS_URL`)
- a `DOCS ↗` link in the app footer (`components/Shell.tsx`)
- a Documentation section in the README, with the `--base` / `--site` invocation
  for a custom domain

## Why no SSG

Docusaurus, VitePress, and Nextra would all do this. All three add a large
dependency tree, a second build system, and their own version of "does the
production build still work", which this repository has a hard-worn reason to
avoid — the app's CI is already the thing that has to stay green.

`scripts/docs/` is ~1000 lines of Node standard library instead: a constrained
Markdown renderer, the ABI generator, the site builder, and a static file server
for local preview. It adds nothing to `package.json`'s dependencies, so the app
build, the app CI, and the docs build cannot interfere with each other.

The trade-off is real and worth stating: the renderer supports a fixed subset of
Markdown (headings, paragraphs, fenced code, GFM tables, lists, blockquotes,
rules, and inline code/bold/italic/links). Anything outside that subset is
rendered as escaped text rather than silently mangled, and an unknown link
target fails the build.

## Safety

The renderer treats all documentation text as untrusted input:

- all text is HTML-escaped; `docs/contract-abi.md` cannot inject markup through
  an endpoint name or description
- `safeHref` refuses `javascript:`, `data:`, and protocol-relative targets
- the generated fragment is HTML rather than Markdown, so it is substituted
  _after_ rendering instead of being escaped into visible text
- `serve.mjs` refuses to serve any path that escapes its root

## Verification

All four gates pass on Node 20.20.2 and the local default:

```
npm run test        48 passed (6 files)   was 31 — 17 added in scripts/docs/docs.test.ts
npm run lint        clean
npx tsc --noEmit    clean
npm run build       8 static routes
```

The 17 new tests cover the parts that fail quietly rather than loudly:

- the generator's output is compared field-by-field against `ABI_ENDPOINTS`
  (run as a subprocess, so it exercises the same transpile-and-import path the
  build uses)
- `docs/contract-abi.md` is asserted to contain no signature strings, no
  Markdown table, and no `<td>` — a pasted table cannot be added without a
  failing test
- removing the anchor, removing the opt-in, and adding a link that names no page
  each fail the build
- no relative page link survives into the output, because a page served at
  `/getting-started/` resolves `./architecture/` to `/getting-started/architecture/`
- `--base /synapse-web/` produces base-prefixed assets, nav, and canonical URLs
- the renderer's inline pipeline leaves a bare `31` in prose alone, joins a
  wrapped list item instead of splitting it, and escapes `<script>`

The site was also driven in a real browser at 1280px and 375px: every internal
link and every table-of-contents anchor resolves, no page overflows
horizontally, no text renders in its own background colour, the copy buttons
attach to all 10 code blocks, and outbound links are marked.

Not verified: a live GitHub Pages deployment. The workflow cannot run in this
repository because the deploy step needs `pages: write`, which requires
`Settings → Pages → Source: GitHub Actions` to be enabled by a repository
admin. The build it runs is the same `npm run docs:build` verified above, and
the base-path assertion in the workflow covers the one mistake that would only
show up after deployment.
